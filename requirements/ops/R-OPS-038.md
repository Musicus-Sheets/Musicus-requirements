# R-OPS-038 Database check in pull requests

## Statement

The continuous integration shall fail a pull request that changes the database other than through a new preview database update.

## Acceptance criteria

- A pull request from a branch not named `release/<version>` that adds a database update file outside `migrations/preview/` fails the check.
- A pull request that modifies or deletes a released database update, or a preview update that is already on `main`, fails the check (outside a release pull request, R-OPS-040).
- The check applies all database updates to an empty database and compares the resulting structure with the checked-in schema snapshot (for example `crates/musicus-server/schema.sql`, generated by `scripts/db-schema.sh`): an outdated snapshot fails, and a changed snapshot without a new preview update fails.
- A pull request that adds a preview update and the matching snapshot change passes.

## Notes

Job `db-check` of the workflow `Database` (Linux only, R-OPS-032); make it a required status check. The snapshot is generated with the real update runner on an empty database and also compared by `cargo test`. Two rules go beyond the criteria above: a new preview's number must be higher than every preview on `main` (development databases apply previews in merge order), and `migrations/releases.txt` changes only in a release pull request. A pull request that changes the snapshot's generator may change the snapshot without a preview. The snapshot diff also makes every schema change visible in review. Code that expects a column no update creates is caught by the `test` job, not by this check.
